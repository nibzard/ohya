# ohya — Measured performance limits

This document records what the hub costs to run, measured on real code paths
with a reproducible corpus. Operators use it to plan disk, memory and time
budgets; engineers use it as the baseline before any optimization. Every
number below was measured on 2026-11-14 on the reference machine in the next
section; absolute values do not transfer to other hardware, but the ratios
and the scaling behavior do.

## Method

All measurements run on synthetic corpora from `internal/fixgen`:
deterministic session generators for every supported agent format (the same
record kinds, field shapes and size distribution verified in each
`testdata/<agent>/README.md`). All three draw texts from one skewed word
distribution, so per-agent numbers differ in record envelope and parser, not
in text volume: mean record size is about 3.2 KB for Claude Code, 3.7 KB for
Codex rollouts and 4.7 KB for Pi sessions. No real transcripts are committed
or required. The same seed always produces the same bytes.

Corpus shape (`internal/fixgen`, `cmd/genfixture`):

- Generators read no clock or environment. Timestamps count from
  2026-01-01T00:00:00.000Z, and sessions start eight hours apart.
- The default shape follows the verified real corpus averages: main
  sessions of about 512 KiB (the real mean is 756 KB per session including
  subagent transcripts) and a mean of two subagent files per session. Each
  subagent file is about a quarter of its main file. The per-session count
  is a uniform draw around the mean, capped at 4.
- Word choice is skewed: the probability index is squared, so the first
  vocabulary words dominate and the tail stays rare. About 3% of texts
  carry one marker word, which gives selective full-text matches. About a
  third of filler lines look like code.
- Claude Code: one file per session under the encoded `cwd` directory, and
  subagent transcripts under `<session>/subagents/` that reuse the parent
  `sessionId` with `isSidechain` and `agentId`. Each assistant response has
  one to four blocks that share one `message.id` and one usage object.
- Codex: one rollout per thread under `YYYY/MM/DD/`. Ordinals start at the
  `session_meta` record. Usage records carry per-response usage plus
  running turn and thread totals, and the cached part stays within
  `input_tokens`. Subagent rollouts open with their own `session_meta` and
  embed the parent's as line two. Resumed pages test write-path
  deduplication, not parse cost, so the corpus omits them.
- Pi: one file per session in the 1.5.2 shape, including the `system`
  entry and `durationMs`. Every assistant message carries one usage object
  keyed by its `responseId`, where `input + cacheRead + output =
  totalTokens` and `cacheWrite` and `reasoning` stay 0. Pi has no subagent
  files, so the subagent setting does not apply.

Tests in `internal/fixgen` pin the generator contract: every file parses
to its end through the production parser and adapter, commits through the
real write path, and a repeated batch inserts nothing.

Reproduce with:

```sh
make bench                                   # ingestion + query benchmarks, 32 MiB corpus
OHYA_BENCH_MIB=128 make bench                # larger volume
go run ./cmd/genfixture -root /tmp/corpus    # on-disk Claude Code corpus
go run ./cmd/genfixture -agent codex -root /tmp/corpus-codex
go run ./cmd/genfixture -agent pi -root /tmp/corpus-pi
make build
/usr/bin/time -v ./bin/ohya ingest --once --claude-root /tmp/corpus \
    --codex-root '' --pi-root '' --db /tmp/hub.db --state /tmp/state
```

The Codex and Pi corpora ingest the same way with `--codex-root
/tmp/corpus-codex` (and the other two roots empty) or `--pi-root
/tmp/corpus-pi`.

Benchmarks write only to temporary directories; profiles and other generated
outputs belong under `perf/` (gitignored).

Reference machine: one shared Linux VM (kernel 6.8, ext4), 12th-generation
laptop CPU reporting 8 cores to Go, Go 1.27.3, CGO build with the SQLite
driver's bundled SQLite, WAL journaling and `synchronous = FULL` — the
shipped durability configuration. The disk serves other tenants, so
fsync-bound numbers vary between runs; every fsync-sensitive figure below
states its observed spread.

## Benchmark corpus fixtures

The benchmarks above run on one agent format at a time. Workloads that must
look like a real hub (T069) use two named mixed-agent fixtures, generated by
`fixgen.ImportMix` and `fixgen.QueryMix` and written by `cmd/genfixture -agent
mix`. Both hold all three agent formats in the proportions of the machine's
observed corpus, measured 2026-11-15:

| Anchor | Claude Code | Codex | Pi |
|---|---|---|---|
| Main sessions/threads | 1,042 | 1,600 (derived) | 74 |
| Mean main file | 1.27 MiB (observed 1.29 GiB / 1,042) | 1.17 MiB (2.93 GiB / 2,495 files) | 28 KiB (2.1 MiB / 74) |
| Subagent files per session | 1.25 (1,280 observed) | 2 (generator default) | none |
| Mean record, full records | 3.4 KB | 3.7 KB | 5.0 KB (2.7 KB at the observed 28 KiB session size) |

The Codex thread count is derived, not observed: the generator omits resumed
pages (they test write-path deduplication, not parse cost), so thread count is
the byte volume divided by one main rollout plus its subagent rollouts. The
fixtures therefore carry Codex's observed bytes and file sizes with fewer,
self-contained threads.

The **import fixture** (`-fixture import`, scale `1/32` of the observed session
counts) keeps real record sizes and real session fan-out at a reduced total:

| Agent | Sessions | Files | Records | Bytes | Mean/max record |
|---|---|---|---|---|---|
| claude-code | 33 | 55 | 15,033 | 48.8 MiB | 3,407 / 25,492 B |
| codex | 50 | 134 | 24,947 | 88.0 MiB | 3,699 / 24,478 B |
| pi | 2 | 2 | 40 | 105 KiB | 2,702 / 21,381 B |
| Total | 85 | 191 | 40,020 | 137.0 MiB | |

The **query fixture** (`-fixture query`) targets about one million events for
the BM25 workload without a 3 GiB input (the perf plan's open question): the
same agent mix and session fan-out with every record's text divided by eight
and session byte targets divided by four, so each session still holds roughly
its real event count. Mean records land at 765–889 B, dominated by the JSON
envelope; total volume shrinks 4.4x per event:

| Agent | Sessions | Files | Records | Bytes | Mean/max record |
|---|---|---|---|---|---|
| claude-code | 729 | 1,303 | 326,614 | 277.2 MiB | 889 / 3,750 B |
| codex | 1,120 | 2,794 | 641,706 | 468.7 MiB | 765 / 3,341 B |
| pi | 52 | 52 | 684 | 539 KiB | 806 / 3,316 B |
| Total | 1,901 | 4,149 | 969,004 | 746.4 MiB | |

Records and events are one to one in every fixture: each parser maps every
parsed record to exactly one event, and `fixgen.MeasureMix` counts through the
production parsers, so the numbers above are event counts, not line counts.

Regenerate (seed 7 is the canonical seed; the same seed reproduces the same
bytes):

```sh
go run ./cmd/genfixture -agent mix -fixture import -root /tmp/ohya-import
go run ./cmd/genfixture -agent mix -fixture query  -root /tmp/ohya-query
make build
/usr/bin/time -v ./bin/ohya ingest --once \
    --claude-root /tmp/ohya-import/claude-code \
    --codex-root /tmp/ohya-import/codex \
    --pi-root /tmp/ohya-import/pi \
    --db /tmp/hub.db --state /tmp/state
```

`genfixture` prints the stats table above (sessions, files, records, events,
bytes, record sizes per agent) on every run. Generating the query fixture
holds it in memory (about 800 MB peak; 21 s on the reference machine). The
import fixture imports end to end as 40,020 events from 191 sources; a second
`ingest --once` pass is a no-op. `BenchmarkIngestCorpusMix` in
`internal/events` runs the same mixed shape in process at
`OHYA_BENCH_MIB` volume.

Determinism is pinned by tests, not convention: `TestAgentCorpusStableHash`
and `TestGenerateMixIsDeterministic` (`internal/fixgen`) assert stable SHA-256
hashes over the generated bytes, so any change to generator output — including
accidental rng-call reordering — fails `make check` until the hash and the
measurements above are repinned together. `TestNamedFixtureStats` regenerates
both named fixtures at full scale and asserts their event counts (40k ±50%,
one million ±5%); it runs only with `OHYA_MIX_VERIFY=1` because it needs about
1 GiB of memory:

```sh
OHYA_MIX_VERIFY=1 go test -tags sqlite_fts5 -run TestNamedFixtureStats -v ./internal/fixgen
```

Generated corpora are never committed. `testdata/bench/` is gitignored for
runs kept inside the checkout; `perf/` holds benchmark output.

## Freshness

Freshness lag is the steering metric: the wall-clock time from a complete,
newline-terminated record appended on a device to that record being returned
by a query through the remote `sql` tool. The harness lives in
`cmd/ohya/freshness_test.go` (`TestFreshnessSmoke`). It drives the real
stack with the child-process pattern of `cmd/ohya/serve_e2e_test.go`: a
`child-serve` hub, a `child-join` uploader, and a remote `child-mcp` observer,
all on one host over the local tailnet path.

Measurement contract (performance plan of 2026-11-15, summarized in
`NOTES.md`):

- Every appended record carries a unique marker (`ohyafresh-<run>-<seq>`),
  and the observer finds it by polling the direct `events` table — never
  `events_settled`, which hides the last ten minutes by design.
- The appender and the observer share one process and one monotonic clock.
  The harness never subtracts wall-clock timestamps from different hosts.
- The append workload runs at a fixed rate with bounded duration and never
  waits for visibility, so queue growth cannot hide behind the measurement.
  Append timing carries a random phase offset against the upload interval
  plus ±10% jitter, reproducible through `OHYA_FRESH_SEED`.
- Polling gives an upper bound on visibility. The report states the polling
  resolution, query durations, sample count, per-sample budget, and both
  timeout classes: samples that missed the budget while visible, and samples
  still outstanding when the drain window closed. Timed-out samples stay in
  the distribution at drain-window lower bounds and are never removed.

Run the smoke check (default configuration, about 100 samples, roughly 45 s):

```sh
go test -tags sqlite_fts5 -run TestFreshnessSmoke -v ./cmd/ohya
```

The test skips under `-short` and on the darwin CI runners, like the serve
end-to-end tests. Knobs, all optional environment variables:

| Variable | Default | Meaning |
|---|---|---|
| `OHYA_FRESH_SAMPLES` | `100` | Records appended per run |
| `OHYA_FRESH_APPEND_EVERY` | `200ms` | Fixed append period (±10% jitter) |
| `OHYA_FRESH_POLL_EVERY` | `100ms` | Observer polling resolution |
| `OHYA_FRESH_TIMEOUT` | `30s` | Per-sample visibility budget |
| `OHYA_FRESH_UPLOAD_EVERY` | `2s` | Uploader `--interval` (the shipped default) |
| `OHYA_FRESH_SEED` | random | Seed for phase offset and jitter |

A run of roughly 100 samples is a smoke check only. Numbers used for p99
claims need at least 1,000 samples and repeated runs (backlog T070); the
in-test run exists to prove the harness and the stack, not to set baselines.
The workload-matrix runs below follow that rule.

Smoke result, 2026-11-15, reference machine, default configuration
(2 s upload interval, 100 samples, 200 ms append period, 100 ms polling,
30 s budget, random phase 1.59 s): lag p50 1.178 s, p95 2.043 s, p99 2.154 s,
max 2.247 s; 223 poll queries, 0 errors, query duration p50 1.4 ms, max
2.4 ms; 0 timeouts, 0 outstanding records; 116 hub events (16 fixture plus
100 appended). The distribution sits just under the upload interval, which
consumes most of the freshness budget before parsing, transport, and commit.
The first exchange through the remote session cost 2 ms because the shared
device node was already up; a cold first dial costs seconds (see the serve
end-to-end notes in `NOTES.md`).

above the 4–6 MiB observed during a pure import. Between auto-checkpoints the
writer appends while scans of the growing `events` table hold read snapshots;
the WAL carries every commit until a checkpoint can complete. Plan WAL
headroom accordingly: tens of MiB, not the single-digit import figure.

### Workload 4: initial import, replay, restart

Fresh hub, fresh device importing the T069 import fixture (191 files,
40,020 events, 137.0 MiB of records at real sizes, all three agents) through
`ohya join`, then a clean device restart and a clean hub restart.
`OHYA_WORKLOAD_IMPORT=1 go test -tags sqlite_fts5 -run TestWorkloadImport -v
./cmd/ohya`. Three runs; visibility of restart markers is observed on the
events table through a read-only connection (the sql-tool path adds about
2 ms, see the freshness workloads).

| Metric | Run A | Run B | Run C |
|---|---|---|---|
| Time-to-memory (join start to last event, 500 ms poll) | 24.576 s | 7m26.173 s | 4m14.925 s |
| Import rate | 5.57 MiB/s | 0.31 MiB/s | 0.54 MiB/s |
| Hub peak RSS / CPU | 91 MiB / 10.08 s | 93 MiB / 12.19 s | 89 MiB / 11.02 s |
| Uploader peak RSS / CPU | 73 MiB / 1.60 s | 76 MiB / 3.29 s | 73 MiB / 2.05 s |
| Hub database size after import | 275 MiB | 277 MiB | 276 MiB |
| Peak WAL size | 14 MiB | 12 MiB | 11 MiB |
| Device restart, recovery to visibility | 6.636 s | 20.149 s | 14.595 s |
| Hub restart, recovery to visibility | no recovery ≤ 3m | no recovery ≤ 3m | no recovery ≤ 3m |

- **Time-to-memory swings with disk contention**, as every fsync-bound number
  in this document does: the same fixture imported in 24.6 s when the shared
  disk was quiet (5.57 MiB/s) and in 4–7.5 minutes under tenant load. CPU
  stays 10–15 s in every run — the path waits on fsync, not compute. The
  proposal budget (10 minutes for a 3 GB corpus) extrapolates to 9–165
  minutes at these rates: it holds only on a quiet disk.
- **Replay is idempotent**: after both restarts the hub holds exactly 40,020
  events plus the delivered restart markers (40,021 when the hub-restart
  marker never landed); no duplicates, no losses. The device-restart pass
  re-probes all 191 sources and delivers one appended record in 6.6–20.1 s.
- **Hub restart exposes a recovery regression** (consistent across every run,
  2026-11-15): a device whose sync connection was established when the hub
  process stopped never re-uploads — its dials time out at the 60 s deadline
  in a backoff loop for at least three minutes. A device that had not yet
  exchanged with the hub connects to the restarted hub in about 20 s, and
  restarting only the join process reconnects it in about 25 s while the
  restarted hub stays healthy. Separately, the restarted hub itself
  intermittently dies with `panic: ipnlocal: watchdog timeout` in
  tailscale.com v1.104.4 (1 of 3 manual restarts). The fault sits in the
  transport layer's reconnection after a peer restart, not in sync or
  storage; it is tracked as the `hub-restart-reconnect` follow-up finding
  from this matrix, with the manual reproduction commands in `NOTES.md`.

### Query latency at one million events

`BenchmarkQuery` seeded from the T069 query fixture under
`OHYA_BENCH_FIXTURE=query` (seed 7, the canonical fixture: 969,004 events,
4,149 sources, 746.4 MiB of records); `TestQueryFixturePercentiles` reports
the percentiles the benchmark mean cannot (150 samples per pattern after 10
warmup, none timed out):

```sh
OHYA_BENCH_FIXTURE=query go test -tags sqlite_fts5 -run TestQueryFixturePercentiles \
    -bench BenchmarkQuery -benchtime 20x -benchmem -v ./internal/mcpserver
```

| Pattern | p50 | p95 | p99 | max | ns/op (bench mean, 20x) |
|---|---|---|---|---|---|
| FTS selective term, ranked, LIMIT 10 | 2 ms | 2 ms | 2 ms | 2 ms | 2.16 ms |
| FTS wide term, ranked, LIMIT 10 | 190 ms | 193 ms | 193 ms | 201 ms | 192.3 ms |
| Session token totals (all 1,901 sessions) | 8 ms | 10 ms | 13 ms | 20 ms | 8.80 ms |
| Recent sessions (indexed, LIMIT 20) | < 1 ms | < 1 ms | < 1 ms | < 1 ms | 78 µs |
| One session's event range (LIMIT 500) | 1 ms | 1 ms | 1 ms | 2 ms | 0.61 ms |
| Annotation paging (NOT EXISTS, LIMIT 100) | < 1 ms | < 1 ms | 1 ms | 1 ms | 130 µs |

Seeding the fixture hub (generation plus 4,149 source ingests) dominates the
run at roughly five minutes; queries themselves answer in seconds of wall
time. The wide BM25 match is the only pattern above the proposed 100 ms p95
budget, and it is the honest number for this fixture: the compact fixture
divides every record's text by eight, so the wide term matches about one
eighth of the corpus. A real-corpus hub at one million full-size events
carries roughly eight times the postings and would land near 1.5 s per wide
match — the same 0.5–1 ms per 1,000 matching events scaling already recorded
for the smaller hubs. Selective search, listings, aggregation and paging stay
at milliseconds and are flat in volume.

### Guardrail verdicts against the proposed thresholds

The perf plan's Phase 0 thresholds were hypotheses to validate; the matrix
results:

| Proposed threshold | Measured | Verdict |
|---|---|---|
| Freshness p95 < 2 s, steady local tailnet | 1.945–1.999 s (W1, 2×1,000 samples) | Pass, ~50 ms margin; the 2 s upload interval consumes the budget |
| Time-to-memory < 10 min for a 3 GB corpus | 24.6–447 s for 137 MiB (W4, 3 runs) → 9–165 min extrapolated | Pass on a quiet disk, fails under disk contention |
| Query p95 < 100 ms at one million events | 193 ms wide / ≤ 10 ms everything else | Fails for the wide BM25 term; every other pattern passes |
| Hub idle RSS < 150 MB | 65–66 MiB (every workload) | Pass |

Missed targets carry direct Phase 1 evidence: freshness is bounded by the
2 s upload pass interval (the plan's "polling and discovery" candidate), and
wide-query latency is bounded by BM25 postings volume (the plan's "FTS5
merge policy" and "settled queries" candidates). Selecting an optimization
stays a separate decision on this recorded baseline; the hub-restart
recovery regression above is a correctness fix, not a performance choice.

## Ingestion

Benchmarks: `internal/events` (`make bench`), end-to-end run of
`bin/ohya ingest --once` over 461 files (200 main sessions plus subagent
transcripts, 138.7 MiB, 43,626 events).

The `internal/events` benchmarks use corpora of `OHYA_BENCH_MIB` MiB
(default 32). Sessions are about 2 MiB (the verified real mean is 2.3 MB per
main session). Claude Code and Codex sessions have a mean of two
quarter-size subagent files; Pi has one file per session. The benchmarks
batch like `cmd/ohya`: 8 MiB reads, one transaction per batch, and
`store.SourceState` before each parse past offset 0. A record larger than
the batch bound extends the read.

- `BenchmarkIngestCorpus` measures a first import. Each iteration opens a
  fresh database, so the rate includes `store.Open` and its migrations.
- `BenchmarkParseCorpus`, `BenchmarkParseCorpusCodex`, and
  `BenchmarkParseCorpusPi` measure the parser alone. The gap to
  `BenchmarkIngestCorpus` is the cost of the write path.
- `BenchmarkIngestReplay` measures a fully repeated batch below the
  committed cursor. This is the cost of a retry after a lost
  acknowledgment and of the uploader's cursor probe.
- `BenchmarkIngestAppend` measures eight records (about one turn) appended
  above a committed prefix of 1,024 records from a 16 MiB session file.
  When the file runs out of append windows, the benchmark opens a fresh
  database with only the committed prefix, so it can serve any `b.N`.

| Path | Result | Notes |
|---|---|---|
| First import, full path | 4–8 MB/s sustained | Store-level benchmark; single-run spread across disk states, 4.42 MB/s at 128 MiB, up to 19 MB/s with a hot page cache |
| First import, end to end | 56 s wall, 12 s CPU, 138.7 MiB | 2.5 MB/s wall on the contended reference disk; CPU is 21% of wall — the path waits on fsync |
| Parser alone (no database) | Claude Code 127–132 MB/s, Codex 173–178 MB/s, Pi 156–159 MB/s | Stable across runs; CPU-bound; `BenchmarkParseCorpus*` over per-agent corpora from one text distribution |
| Idempotent replay validation | 1.0–1.2 GB/s | A fully repeated 2 MiB batch costs about 2 ms: retry after a lost acknowledgment is cheap |
| One live append (8 records, one commit) | 5–33 ms | fsync at FULL synchronous dominates; spread measured across runs |
| No-op polling pass, 461 sources | 0.02 s | Discovery, stat and fingerprint checks per poll |
| Pass that ingests one 2-record turn | 0.13 s | Near-real-time within the default 2 s poll interval plus about 0.1 s of commit |

CPU profile of the ingest benchmark (5 runs, `perf/ingest-cpu.prof`): 67% of
CPU samples sit inside `runtime.cgocall` — SQLite executing inserts and
commits in C — and 8–15% in `encoding/json` decoding; `store.Ingest`
accumulates 64% cumulative. CPU samples cover only about a quarter of wall
time: the process waits on fsync, not on Go code. No ohya-level Go function
is hot, so no Go-side optimization is justified; the levers are durability
settings and batch size, which are deliberate design choices, not accidents.

Extrapolation: a history the size of the verified real corpus (about 2 GB)
imports in 4–13 minutes wall (about 2 minutes CPU) on comparable hardware.
Ingestion work is linear in bytes: the per-byte rate is flat from 4 MiB to
128 MiB corpora within measurement noise.

## Queries

Benchmarks: `internal/mcpserver` over the seeded hub, plus one probe through
the real `ohya mcp` stdio tool (JSON-RPC round trip included) against the
335 MiB end-to-end hub with 43,626 events. The sql tool's default limits
apply: 5 s deadline, 500 rows, 256 KiB output.

| Query pattern | 32 MiB hub | 128 MiB hub | 335 MiB hub, real stdio |
|---|---|---|---|
| FTS selective term (rare word, ranked, LIMIT 10) | 0.11 ms | 0.16 ms | 0.6 ms |
| FTS wide term (common word, ranked, LIMIT 10) | 4.9 ms | 20.9 ms | 25.3 ms |
| Session token totals (GROUP BY over all sessions) | 0.27 ms | 1.1 ms | 4.1 ms |
| Recent sessions (indexed ORDER BY, LIMIT 20) | 0.05 ms | 0.06 ms | 0.7 ms |
| One session's event range (LIMIT 500) | 1.5 ms | 1.2 ms | — |
| Annotation paging (NOT EXISTS, LIMIT 100) | 0.10 ms | 0.10 ms | — |

Every measured pattern answers at least two orders of magnitude inside the
5 s deadline. Selective search, indexed listings and paging are flat in
corpus volume. Wide full-text matches scale with the number of matching
postings — about 0.5–1 ms per 1,000 matching events at this scale — so a
10x larger hub keeps wide matches in the hundreds of milliseconds.

## Database size

The end-to-end hub holds 138.7 MiB of source records as 351.6 MB (2.42x
input). The multiplier is structural: every record stores its original JSON
verbatim, the normalized searchable text, compact metadata, and the FTS5
index over that text. Plan about 2.5x the transcript volume for the hub
database, plus the same again temporarily for a `VACUUM INTO` backup.

During sustained import the write-ahead log stays bounded by SQLite's
automatic checkpoint: about 4–6 MiB observed, cycling as checkpoints keep
up. A clean process stop checkpoints and removes the WAL.

## Memory

The import streams bounded batches, so memory does not grow with corpus
size: peak resident set size of the full 138.7 MiB end-to-end import was
27.7 MB (about 28 MB including the SQLite page cache). The in-process bound
is one 8 MiB batch plus at most one record at the 1 MiB record limit.
Benchmark allocations through parse plus commit run about 7.3 bytes of
garbage per input byte. Query memory per call is bounded by the row and
byte limits (500 rows, 256 KiB); observed allocations per call are 9–320 KB
depending on row width.

## Regression guards

Two tests fail `make check` on order-of-magnitude regressions; their
ceilings sit far above the measured times so machine-speed drift does not
flake them:

- `TestIngestPerformanceFloor` (`internal/events`): a 24 MiB import through
  the full path must finish inside 30 s (measured about 3 s; a superlinear
  write path blows past the ceiling).
- `TestRetrievalPerformanceCeiling` (`internal/mcpserver`): wide FTS search,
  token totals and annotation paging over a seeded hub must each answer
  inside 2 s (measured under 10 ms; the engine's 5 s deadline is the hard
  bound agents experience).

## Tracking across commits

A single `make bench` run cannot be compared by eye: the fsync-bound
numbers swing several-fold between runs (see above), so any regression
smaller than that spread is invisible. Cross-commit comparison is routine
instead:

```sh
git checkout main && make bench-save          # baseline, COUNT=10 runs per benchmark
git checkout mybranch && make bench-save      # candidate
make bench-diff BASE=perf/bench-<main>.txt NEW=perf/bench-<branch>.txt
```

- `make bench-save` repeats every benchmark `COUNT` times and writes the
  raw run to `OUT`, which defaults to `perf/bench-<commit>.txt`. The
  default of 10 leaves margin over benchstat's minimums (6 samples for a
  confidence interval, 4 to test a difference). Generated output stays
  under `perf/` (gitignored), like profiles.
- `make bench-diff` prints the benchstat table: per-benchmark medians,
  the delta between the two runs, and whether that delta is statistically
  distinguishable from run-to-run noise. Install benchstat as a pinned
  tool, not a project dependency:

  ```sh
  go install golang.org/x/perf/cmd/benchstat@v0.0.0-20261009192801-be2c69fb417e
  ```

CI automates this (`.github/workflows/ci.yml`, `bench` job): every push
and pull request stores its raw run as the `bench-<commit>` artifact,
restores the baseline the main branch last saved, and appends the
benchstat table to the job summary. The job reports; it does not fail on
a regression. Only same-hardware comparisons are meaningful — GitHub's
runners differ from the reference machine, and even between CI runs the
fsync-bound rows (`BenchmarkIngestCorpus`, `BenchmarkIngestAppend`) swing
with the shared runners' disk contention, while the parse and query rows
are stable. Treat a CI delta as a signal to reproduce locally with
`make bench-save` on both commits, not as a verdict.

## Limits and open items

- All fsync-sensitive numbers (import rate, append latency) vary several-fold
  with disk contention; treat the ranges, not the midpoints, as the limit.
- Measurements cover one machine. End-to-end ingestion is benchmarked on the
  Claude Code format (the largest verified corpus); Codex and Pi are
  benchmarked at the parser (`BenchmarkParseCorpusCodex`,
  `BenchmarkParseCorpusPi`) over corpora drawn from the same text
  distribution: 173–178 and 156–159 MB/s against Claude Code's 127–132 —
  the same order, JSON decode dominating. The write path behind the parser
  is shared and fsync-bound, so the full-path numbers above apply to every
  agent format.
- Query latency is measured warm (page cache hot). A cold hub on a slow disk
  pays storage reads on first access; the 5 s deadline absorbs that at these
  volumes.
- Benchmark comparison across commits is automated only where CI reaches:
  each run is compared against the baseline the main branch last saved, on
  GitHub's shared runners. Comparisons across machines (CI versus the
  reference VM) stay manual: `make bench-save` on both commits, then
  `make bench-diff`.
